# 百度热搜数据格式规范 v2（紧凑 Markdown 分节 + 榜单排名）

| 项 | 值 |
|---|---|
| schema 版本 | `2` |
| 状态 | 冻结（SPRINT-02 · TASK-001）· 由 TASK-002/TASK-003/TASK-004 实现 |
| 生效范围 | `20NN/` 下全部数据文件（含 v1 历史文件） |
| 前身 | v1 紧凑 Markdown（§12）· v0 JSON 分组格式（§12） |
| 数据口径与局限 | 见 [data-notes.md](data-notes.md)：rank 起始日 · 标度漂移 · 断档 · 采样偏差 |

本文件是**唯一权威格式定义**。解析器、写入器、迁移脚本、验收脚本一律以本文件为准；
实现与本文冲突时改实现，不改文档（除走正式修订）。

---

## 1. 为什么是「分节 Markdown」

体积是全量真数据（2163 个文件 / 1,850,921 条）实测，非估算：

| 方案 | 体积 | 占 v0 | 结论 |
|---|---|---|---|
| v0 JSON（`indent=4`） | 228.3 MB | 100% | 缩进 + 重复键名 + 32 字符时间戳是大头 |
| 紧凑 JSON（无缩进） | ≈63 MB | 38% | 省 62%，机器友好 |
| **MD 分节（本规范）** | **53.4 MB** | **23.4%** | **省约 77%**，人可读、diff 友好 |
| MD 单表（每行带标题） | 115 MB | 50% | ❌ 标题重复，省不动 |
| TSV（每行带标题） | 101 MB | 44% | ❌ 同上 |

**关键约束**：必须「按标题分节 + 行内只留 `HH:MM:SS`」。
一旦改成每行都带标题的表格，收益从 77% 掉到 50%，本规范即失去意义。

## 2. 目录与文件命名

- 目录：`YYYY/`（UTC+8 年份）。
- 文件名：`YYYYMMDD 百度实时热点.md`，日期为**该次抓取记录所属日期**。
- 一天一个文件；跨日记录不新建文件（见 §5.3）。
- `board` 记录在 front matter；本次仅支持 `realtime`，多榜单并行采集不在 v2 范围内。

---

## 3. 文件结构

```
---
schema: 2
date: "2025-03-08"
timezone: "+08:00"
board: realtime
source: "https://top.baidu.com/board?tab=realtime"
snapshots: 24
titles: 430
records: 1224
generated: "2026-10-12T18:05:00+08:00"
---

## 始终保持弄潮儿的角色

- 00:19:29 7974352 1
- 01:13:56 7956248 3

## #郭婞淳夺中国台北东京奥运首金#

- 14:01:44 2474046
```

四段：front matter → 空行 → 若干「标题节」。文件以 LF 结尾，UTF-8 无 BOM。

## 4. Front matter 字段

`---` 围栏，`key: value` 单行，**全部字符串值加双引号**——`+08:00` 与 `2025-03-08`
在 YAML 1.1 里分别会被读成 60 进制整数和日期对象，加引号可避免第三方解析器歧义。

| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | ✅ | **文件内出现的最高行版本**：只含 v1 行为 `1`，出现任一 v2 行为 `2` |
| `date` | ✅ | 文件归属日期，`YYYY-MM-DD`（UTC+8） |
| `timezone` | ✅ | 固定 `+08:00` |
| `board` | ✅ | 榜单，当前 `realtime` |
| `source` | ⬜ | 抓取入口 URL |
| `snapshots` | ✅ | 当日有效快照数（去重后的抓取时刻数） |
| `titles` | ✅ | 标题节数 |
| `records` | ✅ | 数据行总数 |
| `generated` | ⬜ | 文件生成时刻（ISO 8601，含时区） |

解析器**不得**依赖 `generated`；`titles`/`records` 仅作校验冗余，写入时由内容计算。
解析器须同时接受 `schema: 1` 与 `schema: 2`。

## 5. 标题节与数据行

### 5.1 标题节

- 形如 `## <标题>`，`##` 与标题之间恰好一个空格，行尾无空格。
- 节顺序 = 首次出现顺序，迁移与写入都不得重排。
- 空标题（`strip()` 后为空）跳过，并在校验报告中计数。

### 5.2 数据行（v2 核心变更）

```
- <time> <hot> [<rank>]
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `time` | ✅ | 见 §5.3 |
| `hot` | ✅ | 热度原文，见 §6.1 |
| `rank` | ⬜ | **榜单序号**，见 §6.2 |

- 单空格分隔，行尾无空格。
- **2 段 = v1 行（无 rank）；3 段且第 3 段为纯数字 = v2 行**；其余形态判为无法解析的行。
- 同一文件内**允许 v1/v2 行混存**，逐行独立判定，不要求文件级一致。

### 5.3 时间语义

| 场景 | 写法 | 示例 |
|---|---|---|
| 记录日期 == front matter `date` | `HH:MM:SS` | `00:19:29` |
| 跨日记录（日期 != `date`） | `YYYY-MM-DD HH:MM:SS` | `2026-02-26 00:00:00` |

- 时区恒为 UTC+8，行内不写时区。
- **精度为秒，微秒被丢弃**——微秒是爬取调度抖动，无分析价值。
- 已知跨日数据：`20260225`、`20260704` 两个文件各 51 条（v0 用「开始时刻」定文件名、
  用「结束时刻」写记录时间所致；v1 起已改为同一时刻，不再产生新的跨日行）。
- 解析兼容 `T` 分隔符（v0 中有 65,535 条 `YYYY-MM-DDTHH:MM:SS.ffffff+08:00`）。

## 6. 热度与排名

### 6.1 热度 `hot`

- 按原样字符串写出（当前恒为纯数字），不做千分位、不做单位换算。
- v0 存在两种键：`count`（169,404 条，2020-01 ~ 2021-07-21）与 `hot_index`（1,680,517 条，
  2021-07-27 起）。**两者同义，迁移时归一**，热度位置不变；`count` 值 100% 为纯数字，归一无损。
- ⚠️ **`hot_index` 的标度会跨年漂移**（抽样中位数 2020: 286万 → 2025: 555万），
  **禁止跨年比较绝对值**，只能做年内/同话题相对变化。详见 [data-notes.md](data-notes.md)。

### 6.2 排名 `rank`（v2 新增）

- **1 基整数**，表示该标题**在该次快照榜单中的位次**（页面呈现顺序，1 = 第 1 条）。
- **可选字段**：采集端拿不到序号时**不写该字段**——宁缺勿错。
- 同一标题在不同快照可有不同 rank；rank 有升降即反映榜位变化。
- 🚫 **严禁用 `hot` 反推或回填 rank**。
  实测（2026-10-12 线上首跑）：同一快照内 `rank` 与 `hot` **严格同向**（rank 1 热度最高、
  末位最低，51 条 **0 处逆序**）。但"同向"不等于"可反推"，因为：
  1. 反推需要**每个快照的完整榜单**，而历史 v1 存储已丢失同快照内跨标题顺序；
  2. 历史行可能缺热度（该条会被漏掉），反推出的顺序不可靠；
  3. 单调性样本量仅 1 天，置顶/推广位是否加权未验证；
  4. 一旦反推，等于把**推断值**写进数据，混淆可信度等级。
  数据源只记录**实测值**；`rank` 只能来自采集。
- **历史数据没有 rank，且不可恢复**：
  - rank 从未被记录；
  - v1 按标题分节存储，**同一次快照内不同标题之间的先后顺序已丢失**
    （仅每个标题的首次出现顺序保留），故无法反推。
  - 因此 **rank 自 2026-10-12（v2 上线日）起可用**，此前一律视为无排名数据。
- 取值范围校验：`rank >= 1`；同一 `(title, time)` 不应出现两个不同 rank。

## 7. 转义与还原（round-trip 契约）

标题写入 `## ` 之后前先做转义：

| 原字符 | 写出 | 说明 |
|---|---|---|
| `\` | `\\` | 必须最先处理，避免二次转义 |
| LF / CR | `\n`（字面两字符） | 保证一节占一行 |
| 前后空白 | 丢弃 | 抓取端已 `strip()`，不保留 |

**其余字符一律原样保留，不转义**：`#`、`|`、`*`、`` ` ``、`-`、`数字.` 等
在标题行中均无结构歧义。当前数据实测：`#` 开头 2793 条、`-` 开头 15 条、
`数字.` 开头 337 条、`|` 36 条、`*` 6 条、换行 0 条、反斜杠 0 条、前后空白 0 条。

解析时按反序还原（`\n` → 换行，`\\` → `\`）。

> 渲染注意：`## 标题 #`（空格 + `#` 结尾）会被 ATX 规则吞掉末尾 `#`。
> 这是渲染层现象，**数据层以原始行文本为准**；当前数据无此形态。

## 8. Round-trip 契约（验收口径）

1. **记录数守恒**：迁移与读写前后记录数不变（v2 上线基线 = **1,850,921**）。
2. **v1 行**：`(title, time, hot)` 有序序列一致。
3. **v2 行**：`(title, time, hot, rank)` 一致；rank 缺失即字段缺失，**不得写占位值**。
4. **历史文件零改动**：v2 上线不得重写 `20NN/*.md` 历史文件（除当日新增行）。
5. **允许的唯一有损**：微秒 6 位被丢弃。实测仅 4 条记录存在「同标题同秒、不同热度」
   （如 `2021/20210714` · `港大不再承认学生会在校内的角色` · `14:01:44`），
   因逐行存储，记录数仍守恒，不丢行。
6. **不得发生**：标题重排、记录合并去重、热度改写、rank 伪造、日期丢失、文件丢失。

## 9. 排序与幂等

- 节顺序：首次出现顺序（§5.1）。
- 行顺序：时间升序；同秒保持抓取先后（追加顺序）。
- **幂等键：`(title, time, hot)`**（保留 v1 语义，「同标题同秒不同热度」是两条独立记录）。
- `rank` 是幂等键上的**属性**：同一键再次写入时，
  - 新记录带 rank 而旧记录缺 rank → **原地升级**（补上 rank，不新增行）；
  - 其它情况 → 跳过。
- **绝不为同一个键追加第二行。**

## 10. 写入协议（TASK-003/TASK-004 实现）

- **原子写**：写同目录临时文件 → `os.replace()` 替换，禁止原地截断重写。
- **文件锁**：同一文件加排他锁（`fcntl.flock`），防并发抓取互相覆盖。
- **坏文件自愈**：解析失败时把原文件备份为 `<name>.corrupt` 再重建，**不得静默清空**。
- **rank 缺失即缺字段**：采集端解析不到序号时不写 rank，不得写 `0`、「-」或猜测值。
- v1 已修的缺陷：整文件无锁读写（D1）· 5xx 不重试（D2）· 跨日错位（D3）·
  退避硬编码（D4）· 无变更提交失败（D5）· cron 饿死（D6）· 锁文件入库（D7、D8）。

## 11. 解析容错

- 空行忽略；`## ` 起节；`- ` 起行。
- 数据行按「时间前缀 + 剩余空白切分」解析：剩余 1 段 = hot；2 段且末段纯数字 = hot + rank。
- 无法解析的行**保留原文并计入异常报告**，不静默丢弃。
- front matter 缺失：按文件名推断 `date`，并给出 warning。
