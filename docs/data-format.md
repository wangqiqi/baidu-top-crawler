# 百度热搜数据格式规范 v1（紧凑 Markdown 分节）

| 项 | 值 |
|---|---|
| schema 版本 | `1` |
| 状态 | 冻结（TASK-001）· 由 TASK-002/TASK-003 实现 |
| 生效范围 | `20NN/` 下全部数据文件 |
| 前身 | JSON 分组格式（下称 v0，见「兼容与迁移」） |

本文件是**唯一权威格式定义**。解析器、写入器、迁移脚本、验收脚本一律以本文件为准；
实现与本文冲突时改实现，不改文档（除走 TASK-008 修订）。

---

## 1. 为什么是「分节 Markdown」

体积是全量真数据（2163 个文件 / 1,850,921 条）实测，非估算：

| 方案 | 体积 | 占 v0 | 结论 |
|---|---|---|---|
| v0 JSON（`indent=4`） | 228.3 MB | 100% | 缩进 + 重复键名 + 32 字符时间戳是大头 |
| 紧凑 JSON（无缩进） | ≈63 MB | 38% | 省 62%，机器友好 |
| **MD 分节（本规范）** | **≈52 MB** | **≈23%** | **省约 77%**，人可读、diff 友好 |
| MD 单表（每行带标题） | 115 MB | 50% | ❌ 标题重复，省不动 |
| TSV（每行带标题） | 101 MB | 44% | ❌ 同上 |

**关键约束**：必须「按标题分节 + 行内只留 `HH:MM:SS`」。
一旦改成每行都带标题的表格，收益从 77% 掉到 50%，本规范即失去意义。

## 2. 目录与文件命名

- 目录：`YYYY/`（UTC+8 年份），沿用现状。
- 文件名：`YYYYMMDD 百度实时热点.md`，日期为**该次抓取记录所属日期**。
- 归一：v0 期存在 `YYYYMMDD 实时热点.json`（224 个，无「百度」前缀），
  迁移时统一重命名为 `YYYYMMDD 百度实时热点.md`，不再保留双命名。
- 一天一个文件；跨日记录不新建文件（见 §5.3）。

## 3. 文件结构


四段：front matter → 空行 → 若干「标题节」。文件以 LF 结尾，UTF-8 无 BOM。

## 4. Front matter 字段

`---` 围栏，`key: value` 单行，**全部字符串值加双引号**——`+08:00` 与 `2025-03-08`
在 YAML 1.1 里分别会被读成 60 进制整数和日期对象，加引号可避免第三方解析器歧义。

| 字段 | 必填 | 说明 |
|---|---|---|
| `schema` | ✅ | 规范版本，当前 `1`（整数） |
| `date` | ✅ | 文件归属日期，`YYYY-MM-DD`（UTC+8） |
| `timezone` | ✅ | 固定 `+08:00` |
| `board` | ✅ | 榜单，当前 `realtime` |
| `source` | ⬜ | 抓取入口 URL |
| `snapshots` | ✅ | 当日有效快照数（去重后的抓取时刻数） |
| `titles` | ✅ | 标题节数 |
| `records` | ✅ | 数据行总数 |
| `generated` | ⬜ | 文件生成时刻（ISO 8601，含时区） |

解析器**不得**依赖 `generated`；`titles`/`records` 仅作校验冗余，写入时由内容计算。

## 5. 标题节与数据行

### 5.1 标题节

- 形如 `## <标题>`，`##` 与标题之间恰好一个空格，行尾无空格。
- 节顺序 = v0 JSON 的键顺序（即当日首次出现的先后），迁移与写入都不得重排。
- 空标题（`strip()` 后为空）跳过，并在校验报告中计数。

### 5.2 数据行

- 形如 `- <time> <hot>`，单空格分隔，行尾无空格。
- 同秒同一标题出现多条**合法**：逐行保留，不合并、不去重（见 §8）。
- 解析取「时间后的剩余整串」为热度原文，因此热度含非数字字符也不丢。

### 5.3 时间语义

| 场景 | 写法 | 示例 |
|---|---|---|
| 记录日期 == front matter `date` | `HH:MM:SS` | `00:19:29` |
| 跨日记录（日期 != `date`） | `YYYY-MM-DD HH:MM:SS` | `2026-02-26 00:00:00` |

- 时区恒为 UTC+8，行内不写时区。
- **精度为秒，微秒被丢弃**——微秒是爬取调度抖动，无分析价值。
- 已知跨日数据：`20260225`、`20260704` 两个文件各 51 条，
  成因是 v0 用「开始时刻」定文件名、用「结束时刻」写记录时间（见 §10 缺陷 D3）。
- 解析兼容 `T` 分隔符（v0 中有 65,535 条 `YYYY-MM-DDTHH:MM:SS.ffffff+08:00`，
  其余 1,785,386 条用空格），写出统一用空格形式。

## 6. 热度字段与 schema 归一

- v1 只有 `hot` 一个热度位置，位于时间之后。
- v0 存在两种键：`count`（169,404 条，2020-01 ~ 2021-07-21）与 `hot_index`（1,680,517 条，2021-07-27 起）。
  **两者同义，迁移时归一**，热度位置不变。
  已核实 `count` 值 100% 为纯数字，归一无损。
- 值按原样字符串写出（当前恒为纯数字），不做千分位、不做单位换算。

## 7. 转义与还原（round-trip 契约）

标题写入 `## ` 之后前先做转义：

| 原字符 | 写出 | 说明 |
|---|---|---|
| `\` | `\\` | 必须最先处理，避免二次转义 |
| LF / CR | `\n`（字面两字符） | 保证一节占一行 |
| 前后空白 | 丢弃 | 抓取端已 `strip()`，不保留 |

**其余字符一律原样保留，不转义**：`#`、`|`、`*`、`` ` ``、`-`、`数字.` 等
在标题行中均无结构歧义。当前数据实测：`#` 开头 2793 条、`-` 开头 15 条、
`数字.` 开头 337 条、`|` 36 条、`*` 6 条、换行 0 条、反斜杠 0 条、前后空白 0 条。

解析时按反序还原（`\n` → 换行，`\\` → `\`）。

> 渲染注意：`## 标题 #`（空格 + `#` 结尾）会被 ATX 规则吞掉末尾 `#`。
> 这是渲染层现象，**数据层以原始行文本为准**，round-trip 不受影响。
> 当前数据无此形态。

## 8. Round-trip 契约（验收口径）

迁移与读写必须满足：

1. **记录数守恒**：全仓 `records` 合计 = **1,850,921**。
2. **逐文件有序多重集相等**：`(title, time_sec, hot)` 序列在 v0 → v1 前后完全一致。
3. **允许的唯一有损**：微秒 6 位被丢弃。
   实测影响：仅 4 条记录存在「同标题同秒、不同热度」
   （如 `2021/20210714` · `港大不再承认学生会在校内的角色` · `14:01:44`），
   因逐行存储，记录数仍守恒，不丢行。
4. **不得发生**：标题重排、记录合并去重、热度改写、日期丢失、文件丢失。

---

## 9. 排序与幂等

- 节顺序：首次出现顺序（§5.1）。
- 行顺序：时间升序；同秒保持抓取先后（追加顺序）。
- 追加写入幂等：`(title, time)` 已存在则跳过，重复执行同一抓取不产生重复行。

## 10. 写入协议（供 TASK-003 实现）

- **原子写**：写同目录临时文件 → `os.replace()` 替换，禁止原地截断重写。
- **文件锁**：同一文件加排他锁（`fcntl.flock`），防并发抓取互相覆盖。
- **坏文件自愈**：解析失败时把原文件备份为 `<name>.corrupt` 再重建，**不得静默清空**。
- **v0 缺陷（本 Sprint 一并修）**：
  - D1 整文件 read-modify-write，无锁 → 重叠运行丢数据
  - D2 `RequestException` 直接抛出 → 5xx 不重试
  - D3 文件名取开始时刻、记录时间取结束时刻 → 跨日错位（§5.3）
  - D4 `RETRY_DELAY` 硬编码、日志用模块级 `logging`

## 11. 解析容错

- 空行忽略；`## ` 起节；`- ` 起行。
- 无法解析的行**保留原文并计入异常报告**，不静默丢弃。
- front matter 缺失：按文件名推断 `date`，并给出 warning。
